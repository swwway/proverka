# проверка

**Одна команда, которая не умеет соврать зелёным.**

Инструмент отвечает на вопрос «работает ли то, что я только что сделал» — и
различает три исхода вместо двух: сделано, сломано и **не проверено**. Последний
и есть весь смысл: прогон, в котором не запустилось ничего, тоже возвращает ноль
и выглядит зелёным.

Написан для работы с ИИ-агентами, но полезен и без них: он ловит не ошибки в
коде, а **ложные отчёты об успехе**.

> *A CLI that refuses to report green when nothing was actually verified.
> Three outcomes instead of two: pass, fail, and **unverified**. Includes
> mutation-style self-testing: the tool plants faults in itself and must catch
> every one. Interface and output are in Russian.*

---

## Как это выглядит

Прибор доказывает себя тем же способом, каким проверяет других — подкладывает
себе порчи и обязан поймать все:

```
$ proverka selftest

Подкладываю прибору 8 порч. Не покраснел на любой — прибор негоден.

  [поймал] команда падает                          ждали «красно»
  [поймал] код 0, но запущено НОЛЬ проверок        ждали «не проверено»
  [поймал] команды вообще не существует            ждали «не проверено»
  [поймал] код 0, но в отчёте десять падений       ждали «красно»
  [поймал] всё пропущено, ни одного прогнанного    ждали «не проверено»
  [поймал] честный зелёный прогон                  ждали «зелено»
  [поймал] обязательный вид не покрыт              ждали «не проверено»
  [поймал] зелёное, но код не в коммите            ждали «не проверено»
  [поймал] турникет: ворота прошли, поведение нет  ждали «не проверено»
  [поймал] журнал: последний прогон КРАСНЫЙ        ждали «красно»
  [поймал] журнал: последний прогон ЗЕЛЁНЫЙ        ждали «зелено»
  [поймал] задание по проекту без проверок         ждали «не проверено»
  [поймал] набор не усыхает при перезаведении      ждали «обе команды»

Прибор годен: поймал все порчи (13 из 13)
ИТОГ: 13/13 проверок пройдено
```

А так выглядит третий исход в жизни — инструмент не сказал «всё хорошо», он
сказал, чего не знает и почему:

```
$ proverka check ~/projects/мой-проект

ИСХОД: НЕ ПРОВЕРЕНО — по этому проекту уже идёт другой прогон.
  Два прогона дерутся за одну тестовую базу и дают выдуманное
  красное. Дождись первого и запусти снова.
```

## Зачем это нужно

Обычная проверка отвечает «прошло» или «упало». Отсюда две дыры, и обе тихие.

**Ноль проверок — это тоже «прошло».** Прогон, в котором не запустилось ничего,
возвращает код 0 и выглядит зелёным. Сломался сбор тестов, переименовали папку,
не поставились зависимости — и набор молча стал пустым. Отчёт скажет
«проверено», а проверено не было.

**Проверка, которая не умеет краснеть.** Сторож с опечаткой в шаблоне зелёный
всегда. Он не защищает ни от чего, но выглядит защитой. Замерено на живых
проектах: из пяти сторожей, поставленных за одни сутки, пять оказались полыми —
они искали то, чего в файле никогда не бывает.

Инструмент закрывает обе.

---

## Коды возврата

Ровно три, и это не украшение — на них построено всё остальное.

| код | исход | значит |
|---|---|---|
| `0` | ЗЕЛЕНО | сделано, и есть чем доказать |
| `1` | КРАСНО | сломано, и известно где |
| `2` | **НЕ ПРОВЕРЕНО** | не смотрел, не смог, не дошёл |

«Не знаю» никогда не превращается в зелёное. Код 0 при нуле запущенных
проверок — это исход `2`, а не `0`.

## Установка

Нужен Python 3.8+ и git. Больше ничего обязательного.

```bash
git clone https://github.com/Artithea/proverka.git
cd proverka
mkdir -p ~/.local/bin
cp proverka proverka-hook-push proverka-klyuchi proverka-vosstanovlenie ~/.local/bin/
chmod +x ~/.local/bin/proverka*

# если ~/.local/bin не в PATH:
echo 'export PATH="$HOME/.local/bin:$PATH"' >> ~/.bashrc && source ~/.bashrc
```

**Первым делом — убедиться, что прибор годен:**

```bash
proverka selftest
```

Ждём «поймал все порчи (13 из 13)» и код возврата 0. Не так — не пользуйтесь,
сначала разберитесь почему.

### Отправка итогов в Telegram — необязательно

```bash
mkdir -p ~/.config/proverka
cat > ~/.config/proverka/telegram.env <<'EOF'
TELEGRAM_BOT_TOKEN=123456:AA...
TELEGRAM_ADMIN_CHAT_ID=123456789
EOF
chmod 600 ~/.config/proverka/telegram.env
```

Либо переменными `PROVERKA_TG_TOKEN` и `PROVERKA_TG_CHAT`. Ничего не настроено —
инструмент просто не отправляет, молча и без ошибок.

## Восемь режимов

| команда | что делает |
|---|---|
| `proverka init <путь>` | обойти проект, **попробовать запустить** каждого кандидата в проверки и записать только то, что реально отработало |
| `proverka check <путь>` | прогнать записанное и напечатать справку по трём исходам |
| `proverka profile <путь>` | какие **виды** проверок обязательны этому проекту и каких нет |
| `proverka gate <путь>` | турникет перед отправкой: только быстрые проверки |
| `proverka teeth <путь>` | подложить в проект порчи и убедиться, что его собственные проверки их ловят |
| `proverka watch <путь>` | сторож против тишины: идут ли прогоны по расписанию вообще |
| `proverka zadanie <путь>` | составить задание на то, что ничем не покрыто |
| `proverka selftest` | доказать, что сам прибор умеет краснеть |

### Чем `init` отличается от «просто найти тесты»

Он не верит конфигурации. Он **запускает** каждого кандидата и записывает только
тех, кто реально отработал и вернул код возврата. Команда, объявленная в
`package.json`, но падающая на отсутствующей зависимости, в набор не попадёт — и
не создаст иллюзию покрытия.

## Как применить ко всем своим проектам

Порядок один и тот же для каждого. Занимает минуты.

**1. Завести проверку**

```bash
proverka init ~/projects/мой-проект
```

Создаст в проекте `КАЧЕСТВО.yml` — список того, что реально запускается.
Прочитайте его: видно, что инструмент нашёл, а что нет.

**2. Посмотреть, чего не хватает**

```bash
proverka profile ~/projects/мой-проект
```

Скажет, какие виды проверок обязательны проекту такого типа. Есть экран — нужен
браузерный прогон. Считаются деньги — нужны эталоны на числа. Не хватает вида —
это честное «не проверено», а не зелёное.

**3. Написать недостающее**

```bash
proverka zadanie ~/projects/мой-проект
```

Составит задание: что не покрыто и с чего начать. Отдайте агенту или сделайте
руками.

**4. Убедиться, что написанное умеет краснеть**

```bash
proverka teeth ~/projects/мой-проект
```

Подложит порчи и проверит, что новые проверки их ловят. **Шаг обязательный.**
Тест, который не краснеет на сломанном коде, хуже отсутствия теста: он создаёт
ложную уверенность.

**5. Поставить турникет перед отправкой**

```bash
cd ~/projects/мой-проект
cp ~/.local/bin/proverka-hook-push .git/hooks/pre-push
chmod +x .git/hooks/pre-push
```

Честно: `git push --no-verify` обходит любой местный хук. Настоящая защита —
проверки на стороне GitHub, а турникет ловит очевидное раньше и дешевле.

**6. Поставить в расписание — вместе со сторожем**

```cron
15 6 * * * ~/.local/bin/proverka check ~/projects/мой-проект >> ~/logs/проверка.log 2>&1
15 7 * * * ~/.local/bin/proverka watch ~/projects/мой-проект >> ~/logs/сторож.log 2>&1
```

Сторож важнее, чем кажется. Обычная проверка молчит, когда её не запустили, и
это неотличимо от «всё хорошо». Сторож смотрит на другое: жива ли строка в
расписании и дописывается ли журнал.

**7. Повторить для каждого проекта.** Порядок тот же, но читайте вывод каждого:
`profile` у разных проектов скажет разное.

## Спутники

**`proverka-klyuchi` — карта ключей.** Ротация промахивается не потому, что
забыли поменять, а потому что не знали про все места, где ключ лежит.
Показывает, какой секрет в каких файлах повторяется. **Никогда не печатает само
значение** — только вид, отпечаток первых символов и список файлов. Отпечатка
хватает, чтобы сказать «это тот же ключ», и не хватает, чтобы его узнать.

**`proverka-vosstanovlenie` — учение по восстановлению.** Копия, которую ни разу
не разворачивали, — не копия, а надежда. Берёт свежий дамп каждой базы,
поднимает временный postgres в контейнере, разворачивает и считает строки.
Красное здесь не только отказ, но и «развернулось, а строк ноль»: пустая база
разворачивается успешно, и по коду возврата это успех. Требует docker.

**`proverka-hook-push` — турникет.** Двое ворот: быстрые проверки и поиск
секретов. Поиск секретов работает **всегда** и закрыт наглухо — не смог
отработать, отправка не проходит. Молчащий сторож секретов опаснее его
отсутствия.

---

## Чего этот инструмент не делает

Не пишет за вас тесты. Не находит ошибки в логике. Не заменяет ревью.

Он делает ровно одно: **не даёт назвать зелёным то, что не проверено.**

## Происхождение

Собран в работе с ИИ-агентами на нескольких живых проектах в 2026 году. Каждое
правило внутри стоит за конкретным случаем, когда без него что-то сломалось
молча. Комментарии в коде эти случаи описывают — их стоит читать, они и есть
самое ценное.

Даты в комментариях настоящие, имена проектов убраны.
